# Режимы работы и сигнальные цепочки

## Цель документа

Этот файл описывает не железо, а поведение системы. Это важно, потому что клиент обычно формулирует задачу через "как аппарат должен работать", а не через "какие микросхемы внутри".

## Основные режимы

Для первой версии рекомендуется заложить следующие состояния:

1. Выключено
2. Инициализация
3. Ожидание
4. Исходящий вызов
5. Входящий вызов
6. Режим разговора
7. Передача от A к B
8. Передача от B к A
9. Ошибка линии
10. Низкий заряд питания

## Сценарий включения

После подачи питания блок должен:

1. Проверить внутренние напряжения.
2. Проверить готовность контроллера.
3. Проверить оптический интерфейс.
4. Перейти в режим ожидания.
5. Отобразить пользователю состояние через индикацию.

Если линк недоступен, блок не должен молча "делать вид, что работает". Пользователь должен явно видеть, что линия не готова.

## Сценарий вызова

### Исходящий вызов

1. Пользователь нажимает кнопку вызова.
2. Контроллер формирует команду вызова.
3. Команда отправляется на удалённый блок.
4. Удалённый блок включает индикацию и, при необходимости, звуковой сигнал.
5. Локальный блок показывает состояние "вызов отправлен".

### Входящий вызов

1. Удалённый блок получает команду вызова.
2. Включается световая и/или звуковая индикация.
3. Пользователь удалённого блока принимает вызов.
4. Система переходит в разговорный режим.

## Сценарий разговора при полудуплексе

Если сохраняется логика существующего аппарата, то наиболее вероятная модель такая:

- в конкретный момент времени активна только одна сторона передачи
- вторая сторона находится в приёме
- переключение направления делается кнопкой передачи, логикой линии или комбинацией этих факторов

### Передача A -> B

```text
Микрофон A
  -> предусилитель A
  -> фильтрация A
  -> АЦП / кодек A
  -> контроллер A
  -> оптический передатчик A
  -> волокно
  -> оптический приёмник B
  -> контроллер B
  -> ЦАП / кодек B
  -> усилитель B
  -> громкоговоритель B
```

### Передача B -> A

Цепочка полностью зеркальная.

## Какие служебные сигналы нужны кроме аудио

По волокну желательно передавать не только голос, но и служебные флаги:

- вызов
- подтверждение связи
- направление передачи
- занятость канала
- ошибка линии
- состояние удалённого питания, если это нужно пользователю

## Логика полудуплекса

Есть три способа сделать полудуплекс:

### Вариант 1. Жёсткая кнопка передачи

Плюсы:

- понятное поведение
- минимум автоматической логики
- проще отладка

Минусы:

- менее комфортно для пользователя

### Вариант 2. Автоматическое переключение по голосовой активности

Плюсы:

- привычнее в использовании

Минусы:

- больше риск ложных срабатываний
- сложнее отладка в шумной среде

### Вариант 3. Гибрид

Кнопка передачи остаётся основным способом, но контроллер помогает с антидребезгом, тайм-аутами, защитой от конфликтов и блокировкой одновременной передачи.

Для первой версии наиболее здраво использовать именно гибридный подход.

## Приоритеты логики

Если события конфликтуют, приоритеты лучше задать так:

1. Авария питания
2. Ошибка линии
3. Активный разговор
4. Входящий вызов
5. Исходящий вызов
6. Ожидание

Это позволит не терять критичные статусы под красивой, но второстепенной индикацией.

## Что должен делать контроллер при обрыве оптики

При потере линка система должна:

1. Остановить разговорный режим.
2. Выключить состояние "канал активен".
3. Включить индикацию неисправности.
4. Периодически проверять восстановление канала.
5. После восстановления вернуть систему в безопасный режим ожидания, а не в самопроизвольный разговор.

## Поведение при низком заряде

Если питание автономное, то лучше разделить два порога:

- предупреждение о низком заряде
- аварийное отключение для защиты батареи и исключения хаотичной работы устройства

В режиме низкого заряда желательно:

- ограничить максимальную громкость при необходимости
- сохранить индикацию
- не допустить зависаний контроллера

## Требования к задержке

Для голосовой связи комфортна малая задержка. Поэтому транспорт должен быть простым.

Практически это означает:

- не использовать тяжелую пакетную архитектуру, если нет необходимости
- не вводить длинные буферы
- не перегружать тракт избыточной цифровой обработкой

Для первого прототипа целевой принцип простой: пользователь не должен ощущать "рацию через компьютер".

## Что полезно предусмотреть сразу

- счётчик потери линка
- счётчик нажатий вызова
- индикацию внутренней ошибки
- контроль зависания прошивки через watchdog
- сервисный режим диагностики

## Итоговая логика версии 1

Версия 1 должна быть не максимальной по функциям, а предсказуемой:

- включился
- показал готовность
- дал вызвать второй блок
- обеспечил устойчивую речь по оптике
- корректно отработал ошибку линии
- не ушёл в непонятные состояния при шуме, просадке питания и потере сигнала
