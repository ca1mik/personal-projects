# Дозор заявок · проверяемый прототип

Проверяет путь тестовой заявки: **страница → заполнение формы в браузере → отправка → запись с той же уникальной меткой в тестовой CRM**.

Это самостоятельный эксперимент по идее «охранника заявок», не часть «Контура». Его база, процесс и порт отделены от производственного демо. Реальные сайты, почта, CRM и Telegram-оповещения не подключены. Платёжеспособный спрос пока не проверен.

## Запуск на Windows

Нужны Python 3.12+ и установленный Microsoft Edge. Откройте `Start.cmd`, затем **http://127.0.0.1:8782/**. Первый запуск устанавливает зависимости из PyPI. Оставьте окно сервера открытым, остановка — Ctrl+C.

Ручной запуск:

```powershell
py -3 -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python -m uvicorn app:app --host 127.0.0.1 --port 8782
```

Браузер проверки запускается отдельно, без сохранённого пользовательского профиля. На Windows по умолчанию используется установленный Edge. Системный Edge не переустанавливается. На Linux/macOS установите Chromium командой `.venv/bin/python -m playwright install chromium` и используйте `.venv/bin/python`.

Если нужен другой порт, задайте совпадающий адрес и порт сервера:

```powershell
$env:GUARDIAN_BASE_URL = 'http://127.0.0.1:8783'
.venv/Scripts/python -m uvicorn app:app --host 127.0.0.1 --port 8783
```

Адрес доступен на этом компьютере. Это не публичная ссылка для проверки с телефона. Приложение рассчитано на локальный запуск без многопользовательской авторизации.

## Как попробовать

1. Выберите **«Всё работает»** и нажмите «Проверить путь заявки». Проверяющий откроет собственную форму в браузере и заполнит вымышленные данные. Итог «Доставлена» появится только при наличии точной метки этой заявки в тестовой CRM.
2. Выберите **«Тихая потеря заявки»** и повторите. Форма покажет «Спасибо», но запись не сохранится. Проверяющий ожидает до трёх секунд и отмечает потерю. Старая успешная запись из предыдущего запуска не засчитывается.
3. Выберите **«Ошибка сервера»**. Отправка вернёт HTTP 503. Итог — обнаруженная ошибка отправки.
4. Откройте «Снимок страницы» и сравните со статусом: само по себе «Спасибо» не подтверждает доставку.
5. История кликабельна. Результаты, метки и квитанции сохраняются в `data/guardian.sqlite3`, снимки — в `artifacts/`. После перезапуска завершённые результаты остаются. Прерванный запуск получает ошибку вместо выдуманного успеха.

По кнопке выполняется один проход. Расписания и постоянного фонового просмотра нет. Во время проверки режим заблокирован, второй одновременный запуск отклоняется.

## Что считается результатом

- **Доставлена:** форма отправлена, на странице есть подтверждение и тестовая CRM вернула квитанцию по точной уникальной метке.
- **Сбой обнаружен:** HTTP-ошибка формы либо отсутствие квитанции за три секунды при успешном ответе формы.
- **Проверка не завершена:** например, браузер не запустился или изменился селектор поля. Это ошибка проверки; доставка не подтверждена, но конкретная бизнес-причина поломки не утверждается.

Три секунды — выбранный лимит стенда. Для реальных асинхронных CRM и почты нужны согласованные ожидания, повторные проверки и защита от ложных тревог.

## Ограничения и границы проверки

Форма и CRM — контролируемый локальный стенд в одном приложении. Здесь проверяется работа механизма обнаружения, а не качество интеграции с внешней CRM. Встроенная база играет роль тестового получателя.

Разрешён только собственный loopback-адрес. Интерфейс не принимает произвольный URL. Браузер блокирует запросы к внешним адресам. Форма принимает только `monitor@example.invalid` и метки `guardian-*`; реальные письма не отправляются. Есть проверка Origin, токена изменяющих запросов и Host, но это не полноценная система авторизации для публичного размещения.

Для настоящего пилота потребуются:

- разрешённый сайт и согласованный сценарий без оплаты или реальных клиентских заявок;
- отдельная метка и тестовый получатель, чтобы не засорять рабочую CRM;
- доступ к квитанции доставки через разрешённый API или тестовый ящик;
- безопасное хранение секретов, ограниченный доступ, расписание, повторные попытки и согласованный канал предупреждений;
- проверка готовности клиента оплачивать настройку и сопровождение. Рабочий прототип сам по себе спрос не доказывает.

## Код и проверка

| Файл | Ответственность |
|---|---|
| app.py | Локальный API, тестовая форма/CRM, запуск отдельного процесса проверки |
| check.py | Один проход в реальном браузере через Playwright, ожидание квитанции и снимок |
| store.py | SQLite, результаты и точное сопоставление меток |
| static/ | Панель, форма, история и просмотр снимков |
| tests/test_guardian.py | Доставка, тихая потеря, ошибка сервера, ограничения, перезапуск |

Установка инструментов разработки и тесты:

```powershell
.venv/Scripts/python -m pip install -r requirements-dev.txt
New-Item -ItemType Directory -Force test-results
.venv/Scripts/python -m pytest tests -q --basetemp test-results/new-run
```

Выбирайте новый пустой `--basetemp`. Шесть автоматических тестов не запускают браузер; реальный браузерный проход проверяется отдельно через кнопку приложения.

Аналоги для проверки идеи: Checkly (https://www.checklyhq.com/security/) и Better Stack (https://betterstack.com/website-monitoring), проверены 27.10.2026. Возможное отличие услуги — готовая настройка и сопровождение для небольших студий. Это гипотеза, а не подтверждённая уникальность.

Использование Edge через Playwright описано в официальной документации: https://playwright.dev/python/docs/browsers#google-chrome--microsoft-edge.
