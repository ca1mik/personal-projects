## Состояние на 2026-06-05 (исторический снимок, уже не актуален)

- `ppdstr.online` резолвился в `95.163.244.138`.
- `ppdstr.online` по `HTTP` отвечал `400 Bad Request` от `openresty`.

Это значит, что домены уже заведены у регистратора, но публичный web-сервер пока не привязан к ним корректно.

## Что означает сообщение REG.RU

Сообщение вида `домен не подключён к сайту` в панели REG.RU относится к их собственному конструктору/мастеру сайта.

Если сайт будет жить на вашем сервере, это сообщение можно игнорировать. Критично не это, а три вещи:

1. DNS домена должен указывать на нужный сервер.
2. Сервер должен знать `server_name` домена.
3. На сервере должен быть валидный TLS-сертификат для домена.

## Какой домен использовать как основной

**Это изменилось с 2026-06-05 и нужно решить заново.** Раньше `.online` был ближе к рабочему состоянию; на 2026-06-08 все наоборот - `ppdstr.ru` уже резолвится в рабочий хост и реально отдает сайт (`200 OK`), а `ppdstr.online` все еще указывает на чужой IP (`400 Bad Request`).

Варианты:

- Сделать канонiческим `ppdstr.ru` (он уже работает) и настроить `.online` как алиас с редиректом на `.ru`, как только его DNS укажет на тот же сервер.
- Либо целенаправленно перевести DNS `.online` на новый сервер и сохранить его как канонический, как изначально планировалось - тогда `.ru` станет алиасом с редиректом.

`deploy/nginx/ppdstr.conf` сейчас все еще жестко references `ppdstr.online` как канонический домен (строка с `return 301 https://ppdstr.online$request_uri`). **Перед выкатом на новый VPS обновите этот редирект и `server_name` под фактически выбранный канонический домен**, иначе посетители будут переадресованы туда, где сайта нет.

## Что публиковать на сервер

Публичным web-root должен быть только каталог `site/`.

Не надо публиковать наружу корень всего репозитория, иначе вместе с сайтом будут доступны служебные файлы и внутренние материалы:

- `bot/`
- `docs/`
- `tools/`
- `CODEX_CONTINUATION.md`
- `README.md`
- `.env`, логи и `cmd`-скрипты

## Если сервером будет этот компьютер

Если сайт должен открываться прямо с домашнего или рабочего компьютера, а не с отдельного VPS, нужны еще три условия:

1. DNS-записи домена должны указывать не на старый внешний сервер, а на текущий публичный IP этого компьютера или роутера.
2. На роутере должен быть настроен проброс портов `80` и `443` на локальный IP этого компьютера.
3. На самом компьютере должен работать веб-сервер с TLS-сертификатом для `ppdstr.online`.

Для локального запуска в проект уже добавлен безопасный сервер:

```powershell
python site/scripts/serve_public_site.py --host 0.0.0.0 --port 8812
```

Он публикует только публичные страницы сайта и не открывает наружу `docs/`, `bot/`, `tools/` и внутренние `dashboard`/`vk-kit` страницы.

## Что уже добавлено в проект

В `site/` теперь есть:

- `robots.txt`
- `sitemap.xml`
- `site.webmanifest`
- `favicon.svg`
- canonical/OG-мета для публичных страниц
- `noindex` для внутренних страниц (`index.html`, `dashboard.html`, `vk-kit.html`)

Готовый серверный конфиг лежит в `deploy/nginx/ppdstr.conf`.

## DNS, который нужно проверить

Для `ppdstr.online`:

- `A @ -> 95.163.244.138`
- `A www -> 95.163.244.138` или `CNAME www -> ppdstr.online`

Для `ppdstr.ru`:

- `A @ -> 95.163.244.138`
- `A www -> 95.163.244.138` или `CNAME www -> ppdstr.ru`

Если `ppdstr.ru` всё ещё не резолвится, проверьте:

- что зона реально сохранена и опубликована;
- что домен использует нужные `NS`;
- что у регистратора нет незавершённой делегации или DNSSEC-конфликта.

## Минимальная последовательность на сервере

1. Скопировать каталог `site/` на сервер как отдельный сайт.
2. Подключить `deploy/nginx/ppdstr.conf` в `openresty/nginx`.
3. Заменить пути к `root`, `ssl_certificate` и `ssl_certificate_key`.
   Сертификат в redirect-блоке должен покрывать `ppdstr.online`, `www.ppdstr.online` и, если уже включён редирект, `ppdstr.ru` / `www.ppdstr.ru`.
4. Перезагрузить `nginx`/`openresty`.
5. Проверить:
   - `http://ppdstr.online` должен редиректить на `https://ppdstr.online/`
   - `https://ppdstr.online` должен открывать клиентскую страницу
   - `https://ppdstr.online/offer`
   - `https://ppdstr.online/payment`
   - `https://ppdstr.online/privacy`
6. После появления DNS у `.ru` проверить редирект `ppdstr.ru -> ppdstr.online`.

## Бот и API на VPS (закрывает booking-form блокер)

На 2026-06-08 форма заявки на живом сайте отправляет `POST` на `{origin}/api/booking-request`, а живой хостинг (`ppdstr.ru`, REG.RU shared hosting через `nginx`) отдаёт на этот путь `404` - там нет и не может быть Python-бэкенда. Заявки с сайта прямо сейчас никуда не доходят.

Решение - переехать на VPS и держать сайт и бота на одном сервере за одним `nginx`:

1. Поднять VPS, поставить `nginx` + `python3` + `venv`.
2. Скопировать `site/` как статический web-root (как описано выше) и `bot/` в отдельную рабочую директорию (например `/opt/likatattoo/bot`).
3. Создать `bot/.env` на сервере из `bot/.env.example` со свежими продакшн-значениями. Важно: рабочий `.env` в гитигноре и никогда не копируется автоматически - в частности, `GOOGLE_SHEETS_SERVICE_ACCOUNT_FILE` должен указывать на **линуксовый** путь к JSON service-account (см. `bot/secrets/`), а не на старый Windows-путь `F:\likatattoo\...`.
4. Запустить бота как systemd-сервис по шаблону `deploy/systemd/likatattoo-bot.service` (там же расписаны все шаги). Бот стартует одним процессом и поднимает и Telegram-поллинг, и HTTP API на `127.0.0.1:8080` (`bot/main.py:run_bot` -> `start_robokassa_server`).
5. В `deploy/nginx/ppdstr.conf` уже добавлены `location /api/` и `location /robokassa/`, проксирующие на `127.0.0.1:8080` - этого достаточно, чтобы фронтенд достучался до бота с того же домена. **Дополнительно ничего на фронтенде менять не нужно**: при пустом `data-request-api-url` (как сейчас в `site/client.html`) `client.js` сам берёт `${window.location.origin}/api/booking-request`, и same-origin запрос пойдёт через этот прокси.
6. Перенести `ROBOKASSA_RESULT_URL` / `ROBOKASSA_SUCCESS_URL` / `ROBOKASSA_FAIL_URL` с временного `localhost.run`-туннеля на постоянные `https://<канонический-домен>/robokassa/...` и обновить их в кабинете Robokassa.
7. Проверить:
   - `curl -I https://<домен>/api/booking-request` (ожидаем `404`/`405` от **бота**, не от REG.RU-заглушки - в ответе не будет `Server: nginx` + REG.RU HTML на 769 КБ)
   - реальную отправку формы на сайте и появление лида в `bot/data/bot.db` / Google CRM

## Что ещё не закрыто

Доменная публикация теперь упакована технически, но в контенте остаются задачи перед финальным запуском:

- заменить шаблонные ссылки `Яндекс Карты` и `2ГИС` на реальные карточки;
- убедиться, что формулировка про медицинское образование публично подтверждаема.

И два инфраструктурных решения, которые блокируют запуск формы заявки и оплат:

- **Выбрать VPS-провайдера и поднять сервер** - без этого `/api/booking-request` будет 404 на проде (см. раздел «Бот и API на VPS» выше). Конфиги (`deploy/nginx/ppdstr.conf`, `deploy/systemd/likatattoo-bot.service`) уже подготовлены, осталось применить их на реальном сервере.
- **Определиться с каноническим доменом** (`.ru` уже работает, `.online` пока нет - см. «Какой домен использовать как основной») и привести `deploy/nginx/ppdstr.conf` в соответствие, прежде чем включать редирект на проде.
